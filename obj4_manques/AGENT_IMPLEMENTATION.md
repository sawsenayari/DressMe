# DressMe Objective 4 — LLM Agent

## Current status

The intended primary flow is now: local FashionCLIP image embeddings and
zero-shot visual-label candidates → LLM-generated missing-garment archetypes and
LLM pairwise compatibility judgments → Python outfit counting and marginal
gain bounds → LLM explanation. The notebook's trained compatibility models and
its exported ranking values are not used by this new path.

The 200 photos in `wardrobe/re_polyvore_sample/` were validated: 20 categories,
10 photos each; three exact duplicate-image groups (four extra duplicate
records). The local CPU FashionCLIP encoder produced a 512-dimensional
normalized vector and tentative color/pattern/style labels per image, using
`patrickjohncyh/fashion-clip` revision `7e3ba62ce16b379a1ab479346b66f192e76f51b7`.
The raw images and generated embeddings remain local and are Git-ignored.

The LLM proposed five generic gap archetypes and judged 80 of 2,122 required item
pairs before the 9Router/Groq route rate-limited. Therefore the compatibility
analysis is **incomplete** and no final gap ranking is available yet. The static
notebook `gap_report.json` remains the last-resort fallback only; it is not used
by the LLM compatibility pipeline. The five archetypes are hypotheses, not
products or store recommendations.

The image directory currently contains a Re-PolyVore sample, not verified
personal wardrobe photos. The local FashionCLIP preprocessing succeeds, but
real-user relevance and LLM compatibility accuracy still need evaluation.

## Responsibilities and data flow

1. FashionCLIP converts local wardrobe images to normalized embeddings and
   tentative visual labels; it does not score compatibility.
2. An LLM proposes generic garment archetypes and returns structured
   `compatible` / `incompatible` / `uncertain` pair judgments using a rubric.
3. Python enumerates the notebook-defined core outfit templates using only those
   LLM labels and computes conservative/optimistic gain bounds when judgments
   are uncertain.
4. The agent can answer questions from a completed LLM analysis and inventory
   summary. The notebook report is exposed only as a fallback when no completed
   LLM analysis is available.
5. The final LLM explains the returned evidence. It must not invent gains,
   prices, compatibility, product links, or rankings.

Objective 4 defines gain as the additional valid outfit combinations unlocked
by a candidate. The notebook's deterministic calculation remains the numerical
source of truth. A report result has metadata `source=precomputed_notebook_export`
and `recalculated=false`.

### Current boundary

The LLM compatibility pipeline and Python outfit counter are implemented, but
the actual 200-photo run is not complete. The current cache contains 80 of 2,122
required pair judgments; a complete analysis is deliberately not exposed by the
agent. No static report values have been substituted for missing judgments.

The 200 photos are a balanced Re-PolyVore sample rather than a verified personal

## Prompt and request context

Prompt templates live in `dressme_gap_agent/prompts.py` and identify the active
version with `PROMPT_VERSION`. Version `gap-agent-v6` includes:

- DressMe Objective 4 and the Amine, Yasmine, and Sami persona definitions.
- Grounding rules for numerical claims and explicit precomputed-versus-recalculated
  distinctions.
- Prompt-injection and private-data handling.
- Clarification and language guidance; no request to expose chain-of-thought.
- Concise response guidance.
- A request-language hint and explicit handling of partial `top_k` results, using
  `total_available`, `returned_count`, and `truncated` report metadata.

`DressMeGapAgent.run(message, context=...)` accepts only validated structured
fields:

```python
{
    "persona": "amine" | "yasmine" | "sami",
    "season": "hot" | "cold" | "mid-season" | "neutral",
    "budget_max_tnd": 0.0,
    "wardrobe_counts": {"top": 3, "shoes": 1}
}
```

The builder also accepts the notebook's French season labels and canonicalizes
them for the prompt. This context is explanation context only unless a tool
explicitly confirms that it applied a constraint. In particular, the static
report has no prices, so a budget cannot be checked against it.

## Tool schemas and execution policy

The agent exposes only registered, read-only tools. It returns at most one tool
call per request; application code checks every argument and tool result. No
shell, filesystem, SQL, shopping, or arbitrary-code tool is exposed. The exact
current user-facing schemas are:

```json
{
  "get_wardrobe_summary": {
    "parameters": {
      "type": "object",
      "properties": {},
      "required": [],
      "additionalProperties": false
    }
  },
  "rank_wardrobe_gaps": {
    "parameters": {
      "type": "object",
      "properties": {
        "limit": {"type": "integer", "minimum": 1, "maximum": 8}
      },
      "required": ["limit"],
      "additionalProperties": false
    }
  },
  "get_gap_report": {
    "parameters": {
      "type": "object",
      "properties": {
        "top_k": {"type": "integer", "minimum": 1, "maximum": 10}
      },
      "required": ["top_k"],
      "additionalProperties": false
    }
  }
}
```

`rank_wardrobe_gaps` is exposed only when a complete LLM-judged analysis exists.
`get_gap_report` is the last-resort static fallback; its result says
`source=precomputed_notebook_export` and `recalculated=false`. The report loader
validates IDs, categories, slots, descriptions, and nonnegative integer gains,
and strips `exampleItemId` before sending the result to the LLM.

Internal LLM-as-judge calls use two additional function schemas that are not
offered to the user-facing agent:

- `submit_gap_archetypes({"candidates":[{"slot":"...","description":"...","rationale":"..."}]})`
- `submit_pair_compatibility({"judgments":[{"pair_id":"...","verdict":"compatible|incompatible|uncertain","evidence":"..."}]})`

The application verifies exact pair IDs, rejects missing/duplicate judgments,
and caches results by inventory hash, prompt version, and model route.

## Model route and generation settings

The current route is configured by `DRESSME_LLM_MODEL=GapDetection`. A live
response through that combo reported model ID `openai/gpt-oss-120b`; at least one
actual tool call and final answer completed successfully. This verifies that
specific route and tool-calling path, but does not constitute a comparison
against other models or prove that every fallback entry is healthy.

The compatibility pipeline uses `DRESSME_LLM_COMPAT_MODEL=groq/openai/gpt-oss-120b`
through the same local 9Router URL and key. This pinned route completed candidate
generation and pair-judgment batches; the combo's retired/unavailable fallback
entries previously caused failures.

| Setting | Current value | Evidence/status |
|---|---:|---|
| Temperature | 0.2 | Configured baseline; not experimentally optimized |
| Top-p | Provider default | Omitted; not independently tested |
| Maximum output tokens | 600 | Configured output/cost bound |
| Compatibility-judge output tokens | 1600 | Bounded structured pair batch |
| Request timeout | 30 seconds | Configurable in `AgentConfig` |
| Application retries | 1 | Timeout, 429, and transient 5xx only |
| Maximum retry wait | 2 seconds | Longer `Retry-After` values are not retried |
| SDK retries | 0 | Application layer owns retry policy |
| Tool calls | At most one per request | Validated in the orchestrator |
| Model turns | One for direct answers; two for a tool result and explanation | Fixed bounded flow |
| Pair-judgment batch size | 10 | Larger batch produced malformed tool JSON |

The gateway's combo handles its configured provider sequence. The application
does not claim a fallback happened unless the gateway reports a model ID; the
CLI prints configured route and any model IDs/usage returned by the API.
Retries are not attempted for authentication failures, route/model-not-found,
or other permanent request errors. Failure categories are logged by the
evaluation runner without echoing raw provider payloads.

## Setup and run

From the project directory in PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Set the local API key value and combo name in `.env`; do not commit or share the
key. Keep `DRESSME_LLM_BASE_URL=http://127.0.0.1:20128/v1` when the app and
9Router run on the same computer. Ngrok is unnecessary for that setup.

Run the CLI against the notebook report:

```powershell
$env:PYTHONIOENCODING="utf-8"
python -B -m dressme_gap_agent --report .\gap_report.json "Which missing piece unlocks the most outfits? Give its outfit gain."
```

The report can also be provided by `DRESSME_GAP_REPORT`. The demo fixture is at
`examples/gap_report.demo.json` and should be labelled demo data.

To run local FashionCLIP embeddings for the full sample folder, use:

```powershell
python -B -m dressme_gap_agent.fashion_encoder --wardrobe-dir .\wardrobe\re_polyvore_sample --output-dir .\wardrobe\.dressme-cache\full --batch-size 8
```

The FashionCLIP run is local, uses the pretrained encoder only, and produces
512-dimensional vectors plus tentative attributes; it does not calculate
compatibility. The LLM pair judge uses the same 9Router key, pinned by default to
`groq/openai/gpt-oss-120b` because that model completed structured text tool
calls. No separate API key is required.

Run the bounded LLM compatibility/gap pipeline with:

```powershell
python -B -m dressme_gap_agent.llm_gap_pipeline --inventory .\wardrobe\.dressme-cache\full\wardrobe_inventory.json --cache-dir .\wardrobe\.dressme-cache\llm-gap-direct-v1 --output .\wardrobe\.dressme-cache\llm_gap_analysis_direct_v1.json --batch-size 10 --max-new-pairs 40 --max-candidates 5
```

The pipeline checkpoints pair judgments. Rerun the same command to resume; it
does not resend completed pairs. `rank_wardrobe_gaps` becomes available to the
agent only when the analysis status is `complete`. The current cache has only 80
of 2,122 pair judgments, so no result is ranking-ready.

The unit tests use a generated synthetic shirt image to validate file handling
and FashionCLIP input discovery. The 200 current photos are Re-PolyVore sample
images, not verified personal wardrobe photos. The current 9Router combo has
returned `openai/gpt-oss-120b` for an image request and said it could not see the
image; therefore this pipeline supplies tentative FashionCLIP labels as text to
the LLM, not raw image understanding.

## Fixed live LLM evaluation

`llm_evaluation_cases.json` is a fixed, versioned set of eight cases covering
top gain, comparison, persona framing, season limitations, missing prices,
prompt injection, a general persona question, and a synthetic image smoke case.
The runner writes
machine-readable output including prompt version, tool arguments, report IDs
and gains, response criteria, latency, model IDs, and provider-reported token
usage when available:

```powershell
python -B -m dressme_gap_agent.evaluation --report .\gap_report.json --output .\llm_eval_results.json
```

Automated checks cover expected tool selection and arguments, exact returned
IDs/gains, required and forbidden answer terms, and an injection-specific
non-disclosure check. Persona interpretation, language quality, and whether the
season/budget limitation is communicated correctly also require human review.
The runner reports cost as unknown when provider pricing or the serving provider
cannot be verified; it does not invent a cost.

The notebook's Hit@10/MRR metrics evaluate the deterministic recommender, not the
LLM. Likewise, a fluent explanation does not prove recommendation quality.

The latest recorded **text-only** run is `llm_eval_results_final.json`:
dataset `dressme-gap-eval-v2`, prompt `gap-agent-v5`, 6/7 automated task cases
passed, and mean latency was 1.44 seconds. The mixed prompt-injection case was
safely refused: its non-disclosure check passed, but its task-completion check
failed. Cost was not estimated. This small run is not a claim of stable quality;
it predates the current prompt v6 and does not evaluate the LLM-compatibility pipeline.

The LLM compatibility pipeline uses FashionCLIP-derived text attributes, not raw
image pixels. It uses categorical LLM judgments and deterministic Python outfit
counting to produce gain bounds. Those bounds are estimates because the
compatibility labels are model judgments; they are not the notebook classifier's
predictions or calibrated probabilities.

## Reliability and security

- The OpenAI-compatible client uses a bounded timeout and zero SDK retries;
  transient and permanent failures are surfaced through sanitized application
  errors.
- User input, structured context, garment descriptions, and tool results are
  treated as data. Context fields are allow-listed and type/range checked.
- The report tool is read-only, validates its input, bounds result size, and
  removes local example paths.
- Image handling caps requests at three photos, checks file size/type/dimensions,
  removes EXIF metadata by re-encoding, and sends image data—not local paths—to
  the configured vision endpoint.
- Credentials belong in `.env` or another secret store. `.env` is ignored by
  Git; never print or paste the key.
- A local application and local gateway may still send prompts/results to an
  external upstream model provider. This is not fully offline inference.

These controls reduce specific risks; they are not a claim that the system is
fully secure. The live evaluation includes one injection request, and the
provider/gateway logs and retention settings remain outside this application.

## Fine-tuning decision

Fine-tuning is not performed. Prompt engineering and tool schemas are the right
first intervention because the current tasks are tool selection and grounded
explanation, while gains remain deterministic. LoRA trains low-rank adapter
matrices rather than all model weights; QLoRA additionally quantizes the frozen
base model to reduce training memory. Soft prompt tuning trains virtual input
embeddings; prefix tuning learns vectors inserted into transformer layers.
Full fine-tuning changes all or most model weights and has higher compute and
data costs.

A justified experiment would need a trainable open-weight model, reviewed and
held-out examples of requests/tool arguments/tool results/grounded answers, and
a fixed evaluation set. A hosted 9Router combo does not provide this project's
model weights or training control. No training data or hardware-backed training
experiment is currently available, so fine-tuning remains planned rather than
completed.

## Known gaps

- The report is precomputed and is currently the only registered data tool.
- Runtime deterministic ranking for a supplied wardrobe, persona, season, or
  budget is not connected; budget also requires actual prices.
- The 9Router OpenAI-compatible route did not pass images through in live probes.
  Direct vision inference is implemented but awaits a separate Groq key and a
  successful live test with an actual wardrobe photo.
- No real wardrobe images are currently in the repository; synthetic-image unit
  tests do not measure garment recognition quality.
- The notebook's saved joblib model does not by itself provide all candidate
  embeddings/catalogue rows needed to rank an arbitrary wardrobe.
- No frontend/backend application integration is present in this workspace.
- The fixed LLM evaluation is small; model variability, provider fallback
  behavior, cost, and privacy/retention require further verification.
- No fine-tuning was done, and no comparative model-selection experiment has
  been completed.
